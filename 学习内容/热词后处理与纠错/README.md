# 热词后处理与 FastCorrect 纠错 — 知识点整理

> 来源：CCF IVC 2026 川渝方言导航语音识别竞赛实践（队伍 LynRose_Enigma，初赛第 14 名）
> 覆盖：asr-hotword 音素热词、纯字典替换后处理、微软 FastCorrect 纠错模型的原理、踩坑与对比

---

## 一、问题背景：ASR 为什么写错专有名词

本项目模型为 Data2Vec 2.0 + CTC，解码方式 greedy（Viterbi），**无语言模型**。逐帧取最大概率字符，输出由 7531 字符词典构成。这带来一个典型问题：

| 错误类型 | 例子 | 原因 |
|------|------|------|
| 罕见地名写同音字 | 威州镇→温州镇、得荣县→德荣县 | 词在训练语料中出现少，CTC 头对音近字无偏好区分 |
| 机构名/商圈名写错 | 剑阁县→建格县、鲁能星城→鲁能新城 | 专名组合 OOV，逐字贪心解码缺乏词级约束 |
| 数字/量词错位 | 7座商务车→7充商务车 | 同音字 + 训练分布偏差 |

因为导航语音是**地名密集**场景，这类错误是系统性的大头。修复路线有两条：

```
ASR 输出含专名错误
├── 路线 A：热词后处理（确定性，文本级字符串修正）── ✅ 本项目采用
│     ├── 音素模糊匹配（asr-hotword PhonemeCorrector）── 第 1 轮尝试，翻车
│     └── 纯字典替换（hotword_fix.py）── 4 轮收敛后的最终方案
└── 路线 B：纠错模型（学习式，FastCorrect）── ❌ 本项目尝试后放弃（FC1/FC2）
```

## 二、热词（Hotword）后处理

### 2.1 基本概念

**热词** = 希望 ASR 优先识别正确/被强制修正的词表（人名、地名、机构名、专业术语）。

热词可以注入在 ASR 流水线的两个位置：

| 注入位置 | 方法 | 特点 |
|------|------|------|
| **解码期** | shallow fusion（对热词 token 加 logit 偏置）、WFST 解码图加权 | 影响整个解码过程，实现复杂，需要改推理代码 |
| **后处理期** | 对识别出的文本做字符串级修正 | 不动模型、零推理开销、结果可逐条审计 |

本项目选择**后处理期**，原因：模型冻结、完全可控、比赛时间窗内可快速迭代。

### 2.2 asr-hotword（PhonemeCorrector）原理

出处：HaujetZhao 的 [CapsWriter-Offline](https://github.com/HaujetZhao/CapsWriter-Offline) 抽离的独立组件。

| 项目 | 说明 |
|------|------|
| 依赖 | `pypinyin`（音素化）+ `rapidfuzz`（模糊匹配） |
| 性能 | 5000 条热词处理一句约 20ms |
| 热词语法 | `目标词 \| 别名1 \| 别名2 ~~~ 黑名单1 \| 黑名单2` |

工作原理：

```
热词词表 + 识别文本
      ↓
转为音素序列（中文：拼音声母/韵母/声调；英文：字母）
   —— 支持相似音素匹配：前后鼻音、平翘舌、音调容错
      ↓
FastRAG 粗检索 → AccuRAG 精检索（两级过滤找相似片段）
      ↓
相似度 > 阈值（如 0.85）→ 强制替换为目标词
```

本质：**音素级模糊匹配 + 强制替换**。命中别名的音素片段就替换，黑名单用于防止误触发（如 `傅平 ~~~ 扶贫`）。

### 2.3 为什么音素模糊匹配在本任务翻车（第 1 轮）

第 1 轮用 PhonemeCorrector 全量替换，结果：

| 指标 | 数值 |
|------|------|
| 被修改句子 | 1851 / 3461 |
| dev 105 CER | 2.37% → **4.96%**（严重恶化） |

失败原因拆解：

1. **双向模糊匹配不可控**：阈值内就替换，正确识别也被改。reverted Top3：司机→实际(470)、小区→校区(269)、分钟→1分钟(187)——全是音素近似但语义错误的替换。
2. **导航场景音似地名密集**：专名本身就是"音近字"，模糊匹配把对的改成错的。
3. **变长替换的插入副作用**：`没耽误` 被 `没耽搁` 替换后把右邻"误"字顶走 → `没耽搁误`。

教训：**模糊匹配的召回率换来的是不可审计的误伤率**。后处理场景下，精确比召回重要得多。

### 2.4 最终方案：纯字典替换（4 轮收敛）

| 轮次 | 方案 | dev 105 CER | 关键变化 |
|:--:|------|:--:|------|
| 1 | 音素全替换（PhonemeCorrector） | 4.96% | 1851 句被改，大量误伤 |
| 2 | 词库精确判据 | 3.34% | 只保留 wrong 侧精确等于词库条目的替换，878 kept / 2025 reverted |
| 3 | 子串误伤防护 | — | 三类点名误伤（没耽搁误/自驾车去/旧曲路）全部清零 |
| 4 | 词典收敛 479 对 | **2.6438%** | 高质量小词典替换大而杂词典，400 句修改 |

最终版 `hotword_fix.py` 的核心设计：

```python
pairs_sorted = sorted(pairs, key=lambda p: -len(p[0]))   # ① 错词按长度降序
REVERT_SET = {('久曲路', '旧曲路'), ('经点', '景点')}      # ② 整对禁用
PREV_EXCEPT = {('约后', '约好'): '预'}                    # ③ 前字符上下文例外

for w, r in pairs_sorted:
    start = 0
    while True:
        idx = new.find(w, start)                          # find 循环查找
        if idx < 0: break
        if 上下文例外命中: 跳过该处，start = idx + len(w)
        left_han / right_han = 邻接是否为汉字
        if len(r) > len(w) and (left_han or right_han):
            跳过该处                                          # ④ 子串保护
        new = new[:idx] + r + new[idx+len(w):]            # 执行替换
        start = idx + len(r)                              # ⑤ 游标越过替换产物
```

各机制对应一类已发生的误伤：

| 机制 | 拦截的误伤类型 | 实例 |
|------|------|------|
| ① 按错词长度降序 | 嵌套词对双重替换/被截断 | 先替换长词，短词就不会在产物里再次命中 |
| ② REVERT_SET | dev 实证伤害的整对 | 久曲路→旧曲路（dev 10 次命中 +0.232pp）、经点→景点 |
| ③ PREV_EXCEPT | 特定上下文中的错误触发 | "预约后天"被"约后→约好"改成"预约好天" |
| ④ 子串保护（变长替换邻接汉字） | 插入型误伤 | 没耽误→没耽搁误、自驾去→自驾车去 |
| ⑤ 游标防二次替换 | 替换产物中的子串再次命中 | rfind 重复匹配 bug 的修复 |

设计原则（从 4 轮迭代中提炼）：

1. **精确 > 模糊**：只有词典精确命中才替换，音素相似不作证据。
2. **宁可不改，不可改错**：漏改的代价远小于误改。
3. **每类误伤都要机制性拦截**，而不是无限加特例：子串保护机制化拦截"插入型"，REVERT_SET 只是最后兜底。
4. **词典质量是上限**：1522 对大而杂词典 dev=3.25%，收敛到 479 对高质量后 dev=2.64%。

### 2.5 热词与评测口径的冲突（重要教训）

官方 dev ref 是**按音转写**的：华蓥山写成"华音山"、凡尔赛写成"环尔赛"、苏果写成"苏国"、金开大道写成"京开大道"。

后果：热词把音似字改回规范地名（语义正确），反而与 ref 偏离。dev 105 上 34 句修改 = 变好 1 / 变差 26 / 持平 7。

```
语义正确 ≠ 评测正确
```

结论：**后处理前必须先摸清评测口径**。当 ref 按音转写时，任何语义级修正都会伤分，只能靠词典收敛把伤害压到最小（4.96% → 2.64% 的过程就是不断减小误伤面）。这是本项目热词版最终无法在 dev 上验证增益的根本原因。

## 三、FastCorrect 纠错模型

### 3.1 是什么

微软 [NeuralSpeech](https://github.com/microsoft/NeuralSpeech) 仓库（FastSpeech 作者团队）的 ASR 纠错模型。

| 版本 | 核心思路 |
|------|------|
| FastCorrect | 非自回归纠错：用**编辑距离对齐**代替 token 级 teacher forcing 做训练监督，训练/推理都快 |
| FastCorrect 2 | **迭代解码**（`iter_decode_max_iter`）+ 多候选 **nbest 输入**；不止纠识别错，还能把 `<unk>` 占位符恢复为标点 |

关键点：

```
ASR 输出(含错字/<unk>) → FastCorrect(非自回归/迭代解码) → 修正文本
```

- **训练数据是伪数据**：用 ASR 模型对大规模文本语料做识别，自动构造 `(ASR输出, 原文)` 平行对，不需要人工标注。
- **fairseq 生态**：以 `user_dir` 插件方式加载（`FastCorrectModel.from_pretrained(...)`），与我们的 ASR 模型共用 fairseq 环境。
- 输入格式讲究：字符级空格分词 + `<unk>` 占位标点 + nbest 多条候选 `|||` 拼接。

### 3.2 本项目实践（FC1/FC2，均已放弃）

| 尝试 | 做法 | 结果 |
|------|------|------|
| FC1 | 官方预训练 FastCorrect 模型直接对 ASR 输出推理 | 输入带 `<unk>` 占位标点，效果不达标 |
| FC2 | 自建伪数据微调 FastCorrect 2 | **微调 861 步过拟合，推理 CER 93–99%**，失败放弃，工件全部删除 |

FC2 的伪数据构造（`make_fc_train_data.py`）：

```
对每个词典对 (wrong, right)：
  找训练集中含 right 的句子 → 把 right 换成 wrong 制造 hypo
  hypo = 去标点句.replace(right, wrong)      ← ASR 错误模拟
  ref  = 去标点原句                          ← 正确答案
→ 仅 609 对（另有 nbest_train 13,240 条），字典/拼音表手工补标点字符
```

失败原因分析：

1. **伪数据与真实错误分布不匹配**：用词典对合成的错误太"干净"，模型学不到真实 ASR 的错误模式（连续错字、同音串、长尾地名）。
2. **数据量严重不足**：609 对合成数据做微调 → 灾难性遗忘，泛化崩坏。
3. **输入口径复杂易错**：nbest 构造、`<unk>` 标点占位、字符级空格——训练/推理任何一处口径不一致就全线崩（期间曾专门写 `fix_fc_data.py` 修字典标点问题）。
4. **微调失控**：无严格验证集监控，861 步直接过拟合。

### 3.3 热词后处理 vs FastCorrect 对比

| 维度 | 热词后处理（纯字典替换） | FastCorrect 纠错模型 |
|------|------|------|
| 可控性 | 完全确定性，逐条可审计、可回退 | 概率输出，黑盒 |
| 数据需求 | 人工整理的词典 | 大规模伪平行数据 |
| 修复范围 | 仅词典内条目 | 可学到泛化的错误模式 |
| 主要风险 | 误伤（可用机制拦截） | 过拟合、灾难性遗忘、幻觉 |
| 工程成本 | 极低（纯字符串处理） | 高（训练 + 调参 + 口径对齐） |
| 适合场景 | 专有名词密集、词典可得、时间紧 | 伪数据充足、错误模式系统性强 |

### 3.4 教训总结

- **比赛时间窗内，确定性后处理 > 模型级纠错**：后处理可迭代、可验证、可回退；模型纠错的每一次试错都以天计。
- 若做模型级纠错，三个前提缺一不可：
  1. 伪数据**量大且贴近真实 ASR 错误分布**（词典对合成的"干净"错误没用）；
  2. 微调用**冻结骨干/小 LR + 严格验证集**监控，防过拟合；
  3. 训练与推理的输入口径**完全一致**（nbest、`<unk>` 标点、字符级空格）。
